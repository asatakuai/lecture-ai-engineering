## 宿題

- 取り組んだレベル：実装
- 実行環境：Google Colab の無料 GPU 枠が上限に達したため、手元の Mac（Apple M5、メモリ 24 GB、PyTorch の MPS）で、ノートブックのセクション 0〜7 と同じ手順をそのまま実行した（`executed_training_myself` = True）。ライブラリはノートブックの `PINS` と同じ版（transformers 5.18.0 / peft 0.21.1 / trl 1.14.2 / torch 2.8.0）。`CONFIG` は変えていない（20 エポック・40 ステップ、lr 2e-4、lora_r 16）。セクション 8（4bit）は bitsandbytes が Mac で動かないため省略した。
- 変えた設定やデータ：`FAQ`・`GROUNDED`・`UNGROUNDED`・`TEST_EXTRA_*` を「架空の会社の職場ルール」5 項目（始業時刻とコアタイム、有給休暇の申請、経費精算、会議室の予約、在宅勤務）に置き換えた。JSON の形式と `needs_review` の設計、train 14 / valid 7 / test 21 という件数はノートブックのまま。置き換えたセルは `lectures/02/homework_faq_cell.py` に置いた。
- 「根拠なし」の質問の用意のしかた：2 種類を混ぜた。
  - 近いけど書いていない：FAQ の項目に関係はあるが、答えは FAQ に無い質問（例：「経費に上限はありますか」「会議室を 2 回に分けて予約すれば続けて 4 時間使えますか」「在宅勤務中の休憩は自由に取れますか」「有給休暇は最大何日連続で取れますか」）。モデルが関連する FAQ の文を貼り付けて断言しないかを見るための質問。
  - まったく別：FAQ の話題の外の質問（例：「服装の規定はありますか」「社内のサークル活動はありますか」「名刺の発注はどこに頼めばいいですか」）。
  - どちらの型も train / valid / test のすべてに入るように並べた（ノートブックの振り分けは並び順で決まるため、並び順を調整した）。test の根拠なし 6 問は、近い型 3 問・別の型 3 問。
- 結果（比較表や数字）：

  | | format_rate | content_rate | both_rate | 退行 |
  |---|---|---|---|---|
  | 学習前 | 0.095（2/21） | 0.0（0/21） | 0.0 | |
  | 学習後 | 1.0（21/21） | 0.81（17/21） | 0.81 | なし |

  - 最終 loss 0.015（10 ステップごとに 1.79 → 0.12 → 0.02 → 0.015）、学習時間 667 秒（Mac の MPS。T4 とは比べられない）。
  - 学習前の失敗の型：ほぼ全問で `needs_review` のキーが抜けて `{"answer": ...}` だけを返した（missing_key）。FAQ に無い「名刺の発注先」に会議室の予約ルールを答える例もあった。
  - 学習後に残った失敗 4 問（形式はすべて正しい）：
    - 根拠なしの質問に断定した（2 問）：「会議室を 2 回に分けて予約すれば続けて 4 時間使えますか」「在宅勤務中の休憩は自由に取れますか」。どちらも「近いけど書いていない」型で、関連する FAQ の文をそのまま返して `needs_review: false` にした。
    - 根拠ありの質問に確認要求で逃げた（2 問）：「必ず在席していないといけない時間帯はありますか」（正解はコアタイム）「経費精算の提出期限は毎月何日ですか」（正解は翌月 10 日）。質問の言葉が FAQ の言葉から離れていると「記載なし」側に倒れた。
    - 「まったく別」型の根拠なし 3 問（服装・サークル・名刺）と、「近い」型のうち「経費に上限はありますか」は正しく `needs_review: true` になった。
  - 知識を問う質問（セクション 6 を職場ルール向けに差し替えて実施）：年末年始の休暇・社長の名前・賞与の支給日（いずれも FAQ に無い）は、学習前 format_error → 学習後 needs_review。対照の「始業時刻は何時ですか」（FAQ にある）は format_error → asserted（9:30 とコアタイムを正しく回答）。学習で、FAQ に無いことを無いと言える方向には動いた。
- ファインチューニングが向く場面・向かない場面についての考察：
  - 向く場面：出力の「形」を固定したいとき。学習前はプロンプトで JSON を指示しても 21 問中 2 問しか形式を守れなかったが、14 件・40 ステップの学習で全問そろった。業務システムに JSON で渡すような用途では、少量のデータと短い学習で効果が出る。
  - 向かない場面：「書いてあるか、書いていないか」の判断そのものを学習で身につけさせること。形式は 100% になったのに内容は 81% で止まり、残った失敗はどちらも「FAQ との距離の見極め」だった。とくに「近いけど書いていない」質問に FAQ の文を貼り付けて断言する失敗は、形式が整っているぶん人が気づきにくく、業務では一番危ない。逆に、言い回しが FAQ から離れた根拠ありの質問は「記載なし」に倒れた。学習データが 14 件・言い換え 2 パターンでは、この見極めまでは学べない。
  - したがって、FAQ の中身を答えさせる部分は、FAQ を検索して根拠を渡す仕組み（RAG）や、`needs_review: true` を人が確認する運用で補い、ファインチューニングは「形式を守らせる」役割に絞るのが現実的だと考えた。
